  A code review (dispatched after the first commit, scoped to this task's diff) found one real Important-level bug, independently corroborated by a separate broader-scope review pass: `destroy()` only removes `container` from the DOM - it doesn't reset `js/workspace.js`'s module-level `state`/`root`, so the document-level Ctrl/Cmd+Z/Y shortcuts keep running against the destroyed instance's (now-detached) `layerStack`/`undoStack`, and `performUndo()`/`performRedo()` still call `autoSave()` → the closed-over `onChange` callback → `events.emit('change')`, invoking a host's registered handler on an instance it already destroyed.   Design question first, per the task's own framing: the standalone app has no existing Save/Cancel concept to repurpose - `js/workspace.js`'s `backToGalleryButton` click handler has its own comment explaining why ("Every action auto-saves, so there's nothing to lose by leaving - no confirmation prompt here"), and there is no Cancel affordance or discard-draft behavior anywhere in the app. Two designs were on the table: (a) wire the existing `#back-to-gallery-button` to fire `onSave` instead of its `onRequestGallery` no-op, with a new markup element added for `onCancel` only when supplied, or (b) make both purely programmatic instance methods with no new UI, mirroring `loadImage()`/`getImage()`. Went with (b), for three reasons. Second, symmetry: `onSave` and `onCancel` are asymmetric under design (a) - there's no existing "Cancel" button to repurpose the way there's a "leave workspace" button to repurpose for "Save" - and asymmetric treatment of a paired option is worse API design than a uniform one. Third, scope: design.md's own Risks section warns the mount API's UI-control options "could grow into a large, ad-hoc options surface," mitigated by shipping "only what's specified (hide Gallery, restrict tool list, `onSave`/`onCancel`)" - adding a new Cancel button to `WORKSPACE_MARKUP` is new UI chrome the spec's "Host controls which UI chrome is shown" requirement scenario never asked for (that scenario only bundles Gallery-hiding with tool restriction); a pure instance method adds zero markup. Noted for the record: `spec.md`'s own requirement text nowhere names `onSave`/`onCancel` explicitly (only `proposal.md`/`design.md` do, and design.md's Risks section explicitly locks the scope to exactly these two callbacks) - treated as in-scope on the strength of those two documents plus this task's own presence in `tasks.md`, not as a spec gap to flag back.

  What "Cancel" means for an always-autosaving instance, given there is nothing to un-persist: nothing in IndexedDB is ever at risk (autosave already ran before any host code could react), so `cancel()` cannot mean "undo what was saved" the way a traditional Cancel button would. What's real is the mounted canvas's in-memory state since the last checkpoint a host cares about - `mount()` itself, or its most recent `loadImage()` call - so `cancel()` reverts to that checkpoint, the same "start fresh from what was last deliberately loaded" meaning `js/new-canvas.js`'s own New-canvas flow already has for the standalone app, just host-triggered instead of menu-triggered. A host's own storage layer (task 3.9, not yet built) committing something durable beyond IndexedDB is a separate, later concern that `cancel()` doesn't need to know about - it only ever touches the same in-memory/IndexedDB surface every other instance method here already touches.

  Implementation: two new, always-present instance methods, `instance.save()` and `instance.cancel()`, alongside `loadImage()`/`getImage()`/`on()`/`destroy()` - present regardless of whether `options.ui.onSave`/`onCancel` were supplied, so the instance's method shape stays uniform rather than conditionally existing based on `options.ui` (a host can add the callback on a later `mount()` call without the method surface changing shape). `resolveUiCallback(options, name)` is a new pure resolver in `lib/pixi.js` (TDD'd first, 6 unit tests in `lib/pixi.test.js`, mirroring `shouldShowGalleryChrome`/`resolveEnabledTools`'s "no options" / "no `ui`" / "no `<name>` key" / non-function / independent-per-name coverage shape) - via `loadImage()`'s own exact revert mechanics (`layerStack.loadImage(baselineImageData)` + `canvasView.setLayerStack()` + `startWorkspace()`, reused rather than duplicated: reverting to a snapshot is exactly what loading an image already does), then calls `resolveUiCallback(options, 'onCancel')?.()`. `cancel()` is synchronous (no `destroyed`-after-await window to guard, only the same up-front `destroyed` check every other method has) since `baselineImageData` is already plain `ImageData`, unlike `save()`/`loadImage()`/`getImage()`. - [x] 3.9 Thread `options.storage` (a storage adapter per Phase 2) through to the mounted instance's persistence calls

  Investigation confirmed the prompt's suspicion before any code was written: `mount()` always called `initWorkspace({ projectId: null, ... })`, and `saveProject(id, ...)` (`js/persistence.js`) no-ops - by design, matching Dexie's own `.update()` semantics - whenever `id` doesn't already have a record. So every mounted instance's autoSave() (`js/workspace.js`, fired on every commit) was silently writing nowhere, regardless of which adapter was active; `options.storage` on its own would have been unobservable without also fixing this. `mount()` now generates a real `projectId` via `crypto.randomUUID()` (same generation `lib/pixel-engine/layers.js`'s `Layer` already uses) and fires a new `js/persistence.js` export, `createProjectWithId(id, layerStack, name, thumbnail)`, to actually create that record - `createProjectWithId` exists rather than reusing `createProject()` because `createProject()` generates its own id internally (`generateId()`), and `mount()` needs to choose the id itself so it can hand it to `initWorkspace()` synchronously in the same `mount()` call, without making `mount()` itself async (which would break every existing 3.1-3.8 caller's synchronous-mount usage).

  `createProjectWithId()`'s write is fired at `mount()` time but not awaited - a real race against the first user-triggered autoSave()'s `saveProject()` call for the same id, since nothing serializes "the record exists" against "a write for that id was requested" other than call order. Resolved by routing both through the same per-id write queue (`enqueueWrite`, already used by `saveProject`/`renameProject`/`deleteProject`) rather than adding new synchronization: `enqueueWrite` chains `writeQueues.get(id) ?? Promise.resolve()` synchronously, before either write's own async body runs, so ordering is decided by *when `enqueueWrite` is called*, not by which write's Promise settles first. Since a mounted instance's first draw event can only happen after `mount()` has already returned, `createProjectWithId()`'s enqueue is guaranteed to happen first - proven by `test/persistence.test.js`'s new race test (fires `createProjectWithId()` unawaited, then immediately awaits a same-id `saveProject()`, and confirms the save's fields land on top of the create's record rather than being silently dropped).

  `options.storage` interacts with `options.width`/`options.height`/`loadImage()` only through this one shared `projectId`: it's assigned once at `mount()` and reused across every `loadImage()`-triggered `startWorkspace()` re-init for that instance's whole lifetime - `loadImage()` is "same project, new content" (autoSave()'s `saveProject()` merges the new dimensions/layers into the existing record), not a second project. Confirmed by reading `pluggable-storage-adapter`'s spec and `lib/storage-adapter.test.js`'s contract tests: nothing in either implies persistence should interact with what content an instance starts with beyond that.

  `js/persistence.js`'s `_setStorageAdapter(options.storage)` is called by `mount()` only when `options.storage` is actually supplied, validated first via a new `validateStorageAdapter()` (duck-types `{ load, save, list, delete }` as functions) - unlike `options.ui.*`'s soft-degrade-on-typo precedent (`shouldShowGalleryChrome`/`resolveEnabledTools`/`resolveUiCallback`), a malformed adapter *throws*, matching `validateHostElement`'s existing throw-on-structural-argument precedent: a broken `options.ui.gallery` value just leaves today's chrome visible (cosmetic), but a broken storage adapter would silently drop every save with no signal to the host, which is a correctness/data-loss concern, not a cosmetic one. Omitting `options.storage` entirely leaves whatever adapter is already active (the default Dexie-backed one, unless another still-mounted instance changed it - see below) - unchanged behavior for that half of the option.

  `js/persistence.js`'s `activeAdapter` is module-level, single-slot state - the same shape of state `js/workspace.js`'s own `root` already has (fixed by tasks 3.2/3.5 for exactly this class of cross-instance leak). Decided to inherit that same "one active instance/adapter at a time" limitation rather than build per-instance-scoped storage: design.md's Decisions describe the mount API as deliberately reusing `js/`'s existing module-level-state architecture, and scoping storage independently while every other piece of state (DOM root, undo/redo shortcuts) stays module-level would be an inconsistent, partial fix that still leaves the "single active instance" limitation everywhere else. `destroy()` now calls `_resetStorageAdapter()` unconditionally (harmless/idempotent even when `options.storage` was never supplied) so a torn-down instance's custom adapter can't outlive it and leak into a later `mount()` call or the standalone app sharing the same page.

  Code review (sonnet) on the first commit found the fire-and-forget `createProjectWithId()` call had a worse failure mode than its own "matches autoSave()'s fire-and-forget convention" framing acknowledged: an ordinary `autoSave()` rejection loses one commit, but a rejected `createProjectWithId()` means this instance's `projectId` never gets an initial record, so *every* subsequent autoSave() for the rest of the instance's lifetime silently no-ops too - a compounding failure with no host-visible signal beyond an unhandled promise rejection, which is inconsistent with `validateStorageAdapter()`'s own "a broken adapter should fail loudly" principle. Fixed: the `createProjectWithId()` call now has a `.catch()` that emits a new `'error'` event through the same per-instance emitter `'change'` already uses (`instance.on('error', handler)`) - `events` (`createEventEmitter()`) is now constructed earlier in `mount()`, ahead of this call, instead of after `canvasView` setup, so the emitter exists in time. Also fixed a stale doc comment on `cancel()` that still described `options.storage` as "task 3.9, not built yet."

DOM-dependent behavior (an actual `mount()` call reaching `_setStorageAdapter`/`createProjectWithId`, a custom adapter receiving real `save()` calls from a real pointer-driven stroke, `destroy()` actually restoring the default adapter for a later `mount()`, and the new `'error'` event firing from a broken adapter) has no `node --test` coverage, matching 3.1-3.8's precedent - verified instead via a throwaway Playwright smoke page (served locally, deleted afterward, never committed), driven via a standalone Playwright script (the Playwright MCP browser profile was locked by another concurrent session this time, unlike the direct MCP driving 3.8 used - a session-environment circumstance, not a product or tooling finding).
