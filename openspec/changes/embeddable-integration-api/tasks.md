## 3. Build the mount API (Phase 3)

- [x] 3.1 Give `js/workspace.js` (and `js/new-canvas.js` if in scope for the mounted flow) a constructor-style entry point that accepts a host container element and options, instead of assuming fixed `index.html` element IDs (`js/new-canvas.js` determined out of scope: the mount API's `loadImage`/`getImage` replace the New Canvas flow for embedded use, so it's never part of a mounted instance. `initWorkspace`/`initExport` now take a `root` option, defaulting to `document` — real container-scoped `root.querySelector('#id')` lookups throughout, not a same-page-ID shortcut; scoped to one active instance at a time, not concurrent multi-instance, per an explicit scope discussion with the user since the approved spec doesn't require multi-instance either. All 76 `document.getElementById`/`querySelectorAll` call sites converted. Verified: `npm test` 202/202, full Playwright smoke test of the standalone app with `root` defaulting to `document` — New Canvas, Workspace load, Brush tool, right-panel toggle, draw, Undo, Export panel — no behavior change)
- [x] 3.2 Create `lib/pixi.js` exposing `Pixi.mount(hostElement, options)`, returning an instance with `destroy()` (the `#screen-workspace` markup `initWorkspace`/`initExport` need is an inline template string in `lib/pixi.js`, a deliberate copy of `index.html`'s block rather than a fetched partial or programmatic DOM build — no build step, self-contained/vendorable, per an explicit discussion with the user; drift risk documented inline as a tradeoff, no automated check yet. `mount()` starts a mounted instance on a blank `options.width`×`options.height` canvas, default 32×32, matching `js/new-canvas.js`'s own default — `loadImage`/`getImage`, task 3.3/3.4, aren't built yet. `validateHostElement` (the one pure-logic piece of `mount()`) is unit-tested in `lib/pixi.test.js` via TDD; the DOM/CanvasView/LayerStack-heavy rest of `mount()`/`destroy()` has no jsdom harness available (matches `test/theme.test.js`'s precedent) and was instead verified with Playwright smoke tests, including a repeated-mount/destroy regression (mount → destroy → mount → draw 3 strokes → Ctrl+Z once → click Undo to exhaust — must total exactly 3, not more/fewer) and a standalone-app pass (New Canvas → draw → Ctrl+Z → Export panel open/close-on-outside-click) confirming no behavior change. `npm test` 209/209.

  A code review (dispatched after the first commit) flagged that `bindDomOnce()`'s `document`-level listeners (`js/workspace.js`) and `initExport`'s two (`js/export.js`) accumulate across repeated mount cycles instead of being replaced — real, confirmed via the regression test above (initial fix attempts left Undo permanently stuck enabled, or the Ctrl+Z/Konami-code guards throwing `Cannot read properties of null`). Root-caused to two distinct bugs, both fixed: (1) `#screen-workspace` needs to be a *descendant* of `root`, not `root` itself, since `root.querySelector('#screen-workspace')` never matches the element it's called on; (2) `root` must be a fresh object every `mount()` call, never `hostElement` directly — a host re-mounting into the same div (destroy → mount again) would otherwise make `domBoundRoot !== root` false the second time, silently skipping `bindDomOnce()` (and with it, the Undo/Redo buttons' listeners) entirely. Separately, `js/workspace.js`'s document-level listeners that close only over shared module state (`root`/`state`/`toolButtons`) now bind once ever (`globalListenersBound`), not per-root — safe since one live copy always tracks the current instance; the two that close over `bindDomOnce()`-local `colorPickerPopover`, and `js/export.js`'s two that close over per-call `panel`/`toggleButton`, are removed and re-added each call instead, since bind-once-ever would leave them pointing at stale, possibly-destroyed elements. Also added the `requestAnimationFrame` re-fit `js/app.js`'s `openWorkspace()` already does (web-font-loading layout settling), which `mount()` had dropped.
- [x] 3.3 Implement `instance.loadImage(pngBlobOrImageData)` on top of `lib/pixel-engine/`'s `LayerStack` (`LayerStack.loadImage(imageData)` - a new, DOM-free, TDD'd method in `lib/pixel-engine/layers.js` - replaces the stack's entire content with a single regular (non-Background) layer sized to the given `{ data, width, height }`, discarding every existing layer; distinct from `resize()`, which crops/pads each layer's content in place, because `loadImage()` is the mounted equivalent of opening a new canvas from an existing image, not an edit of whatever was already there. `lib/pixi.js`'s `instance.loadImage(pngBlobOrImageData)` decodes its argument to that shape first - `isImageDataLike()` (duck-typed, unit-tested the same way as `validateHostElement`) passes ImageData straight through; anything else is assumed to be a Blob and decoded via `createImageBitmap()` + an offscreen canvas's `getImageData()` (no FileReader/base64 round trip, no new dependency) - then calls `layerStack.loadImage()`, `canvasView.setLayerStack(layerStack)` (same instance, mutated in place - `setLayerStack` is what actually resizes the `<canvas>` element and repaints, reusing `js/canvas-view.js`'s existing resize path rather than duplicating it), and re-runs `initWorkspace()` (mirrors `js/app.js`'s `openWorkspace()` opening a different project) so the undo stack and every tool/color/panel selection reset to a fresh baseline instead of carrying over state from before the load. `npm test` 216/216 (7 new tests: 3 for `LayerStack.loadImage()`, 4 for `isImageDataLike()`); `decodeToImageData()`'s Blob-decode path needs a real DOM (`createImageBitmap`, canvas 2d context) so it has no `node --test` coverage, matching 3.1/3.2's precedent - verified instead with a throwaway Playwright smoke page (mounted via a local static server, deleted afterward, never committed): `loadImage()` with a real PNG Blob resized the canvas to the image's own 5×3 dimensions; a second `loadImage()` with a raw `ImageData` (no Blob decode) resized to 4×4 and the read-back pixel at (0,0) matched the source exactly; Undo was disabled immediately after each load (fresh baseline) and re-enabled after a subsequent draw, confirming the editor stays fully usable post-load; `destroy()` still cleaned up correctly afterward. No console errors in any of these runs.

  A code review (dispatched after the first commit) flagged two gaps, both fixed: (1) `LayerStack.loadImage()` had no check that `imageData.data.length` matched `width*height*4` - a too-short array would silently zero-pad into a corrupted image with no error at all, a too-long one would throw an opaque native `RangeError` from inside `Uint8ClampedArray.set()`; now throws a clear `RangeError` naming the actual mismatch, stack left unchanged (unit-tested: a too-short array is refused, `stack.width`/layer count stay at their pre-call values). (2) `instance.loadImage()` had no guard against being called after `destroy()` - it would run `layerStack.loadImage()`/`canvasView.setLayerStack()`/`initWorkspace()` against an already-removed container instead of failing loudly; now throws `Error('instance.loadImage(): called after destroy()')`, checked both on entry and again after the (async) Blob decode resolves, since `destroy()` can complete while a decode is still in flight - verified via the same Playwright smoke page (calling `loadImage()` after `destroy()` throws instead of silently no-op'ing). Left as a documented, not fixed, limitation: two overlapping `loadImage()` calls aren't ordering-synchronized (whichever `await` resolves last wins) - noted in `loadImage()`'s own doc comment as an accepted caveat, matching the same assumption `js/new-canvas.js`'s own image-import flow already makes (one call awaited before the next starts).
- [x] 3.4 Implement `instance.getImage({ format })` (PNG/Blob/Base64/ImageData) on top of `lib/pixel-engine/`'s `LayerStack`; refactor `js/export.js`'s panel to call the same underlying encode function rather than duplicating it (checked first, per the task's own instruction: `js/export.js` already has zero encoding logic of its own — it only builds the popover's scale/format/transparent-background UI and hands the user's choice to an `onExport(options)` callback; `js/workspace.js`'s existing `onExport` implementation is the one and only call site that invokes `state.layerStack.toPNGBlob({ scale, format, skipBackground })` directly. So "one encoding path, not two" (design.md) was already satisfied before this task — no shared helper needed and no `export.js` refactor was possible/necessary, since there was nothing duplicated to extract; `instance.getImage()` is simply a second, independent call site of `LayerStack.toPNGBlob()`, exactly like `onExport` is. `format` (default `'png'`) is one axis, not two — `'png'` returns the raw PNG Blob, `'base64'` converts it to a base64 data URL via `FileReader.readAsDataURL`, `'imagedata'` decodes it back to pixels via `decodeToImageData()` (task 3.3's Blob-decode helper, reused rather than duplicated) — all three round-trip through the same `toPNGBlob()` call with no arguments (native resolution, Background included, reference layer excluded, matching `toPNGBlob()`'s own documented default), so they're guaranteed to reflect identical pixels rather than three independently-behaving paths. `toPNGBlob()`'s own multi-format encoding (`'webp'`/`'jpg'`) and scale are deliberately not re-exposed through `getImage()` — that's the Export panel's own surface, per the proposal's phrasing (`getImage({ format })` listed as returning "PNG/Blob/Base64/ImageData", not webp/jpg). `validateGetImageFormat()` (pure format-string validation, TDD'd the same way as `validateHostElement`/`isImageDataLike`) rejects anything outside `'png'`/`'base64'`/`'imagedata'` with a `TypeError`. `npm test` 221/221 (5 new tests for `validateGetImageFormat`); the Blob→base64/ImageData conversions and the `toPNGBlob()` encode itself need a real DOM (`FileReader`, canvas 2d context) so have no `node --test` coverage, matching 3.1–3.3's precedent — verified instead with a throwaway Playwright smoke page (mounted via a local static server, deleted afterward, never committed), chained after `loadImage()` per the task's suggested flow: mounted a 4×4 instance, `loadImage()`'d a solid-red `ImageData`, selected the Pencil tool and clicked the canvas (a real committed drawing action, not a programmatic `LayerStack` call), then called `getImage()` in all three formats — `'png'` returned a non-empty `image/png` Blob, `'base64'` returned a `data:image/png;base64,...` string, `'imagedata'` returned a 4×4 `ImageData` whose pixels reflected the click (no longer uniform red) — confirming the edit was actually visible through every `getImage()` format, not just the loaded starting content. `format: 'webp'` threw `TypeError`; `getImage()` after `destroy()` threw. No console errors.

  Two issues found and fixed before/during this task, both undocumented gaps in earlier phases' code, not new to 3.4: (1) **Blocking bug found by the Playwright smoke test itself**, before code review: `mount()`'s internal `container` wrapper `<div>` (added in 3.2, between `hostElement` and `#screen-workspace`, for the "fresh object every mount() call" requirement — see 3.2's note) had default `display: block` with auto height, breaking the definite-height chain `.workspace-screen { height: 100% }` needs all the way up to `hostElement`; every mounted screen row (topbar, canvas, palette) collapsed to zero/overlapping height regardless of what height the host page gave `hostElement` itself. Existing 3.2/3.3 verification never caught it because neither exercised a real pixel-accurate click on the mounted canvas. Fixed with `container.style.display = 'contents'`, which drops `container`'s own box (making `screenEl` behave as `hostElement`'s direct child for layout, same as the standalone app's `#screen-workspace` under `<body>`) while keeping it a distinct DOM node for the object-identity checks 3.2 already relies on. Verified via the Playwright click above actually landing on the canvas and producing a real, non-uniform pixel change. (2) **Code review** (dispatched after the first implementation pass) flagged that `getImage()`'s `destroyed` guard was only re-checked after the `toPNGBlob()` encode, not after the *second* await (`blobToBase64`/`decodeToImageData`) for the `'base64'`/`'imagedata'` formats — contradicting the method's own doc comment, which claimed the same re-check-after-await pattern as `loadImage()`. A host calling `getImage({ format: 'base64' })` then immediately `destroy()`-ing could get a resolved base64 string back from an instance that was supposed to have thrown. Fixed by awaiting the second conversion step explicitly and re-checking `destroyed` after it too, before returning. Verified with a second throwaway Playwright smoke page: both `getImage({ format: 'base64' })` and `getImage({ format: 'imagedata' })`, raced against an immediate `destroy()`, now reject with `instance.getImage(): called after destroy()` instead of resolving.
